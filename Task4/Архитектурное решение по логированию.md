# Архитектурное решение по логированию

## Список логгируемых событий

[Части системы где необходимо логгирование](../jewerly_c4_model_with_logging.drawio)

### Уровень Info
1. Изменение статуса заказа
- Время изменения
- Идентификатор заказа
- Новый статус
- Предыдущий статус
- Идентификатор пользователя

2. Расчет стоймости заказа
- Время начала и конца расчета
- Идентификатор заказа

3. Поступление нового заказа
- Время получения
- Идентификатор пользователя
- Идентификатор заказа

4. Получение и отправка сообщения в RabbitMQ
- Время получения или отправки
- Названия топика
- Идентификатор сообщения
- Идентификатор заказа (если есть)

5. Загрузка файлов на S3
- Время
- Статус успешности

### Уровень Error
1. Ошибки расчета в MES
2. Исключения в логике API
3. Проблемы с RabbitMQ

## Мотивация

Логгирование позволит:
- Понять где могут потеряться заказы
- Упростить поиск и устранение ошибок
- Анализировать поведение пользователей системы

### Приоритет

Критические части для внедрения логгирования в первую очередь

1. MES
- Здесь происходит расчет стоймости
- Отсюда часто поступают жалобы
- Критически важная часть с точки зрения бизнеса

2. CRM
- Работа с клиентами
- Управляет статусами заказов
- Так же критически важная часть с точки зрения бизнеса

### Безопасность

Логи не должны содержать чувствительных данных:
- Пароли, токены
- Персональные данные (email, номера телефонов)

Для таких данных можно настроить автоматическое редактирование, скрывающее их значение, например:

"email": "username@gmail.com" -> "email": "[REDACTED]"

---

Доступ с логам можно разграничить по ролям:

- DevOps: полный доступ ко всем логам
- Разработка: доступ к логам своих систем
- QA: доступ к логам dev и release окружению
- Администрация: доступ к отдельно подготовленным агрегированным данным

### Политика хранения

На каждый сервис заведем отдельный индекс в Elasticsearch

Срок хранения в продакш среде установим в 90 дней

Срок хранения в dev и release среде установим в 14 дней

Используя ILM настроим размер каждого индекса до 50Гб, после создается новый индекс. 

## Алертинг

Возможные ключевые метрики для срабатывания автоматического алерта

- Частые ошибки расчета стоймости в MES (10 ошибок за 5 минут). Сигнализирует о массовом сбое расчета.
- Долгие расчеты (более 20 минут на расчет). Сигнализирует о высокой нагрузке
- Частые 500 ошибки в API (50 за 10 минут). Возможен сбой в работе отдельных эндпоинтов
- Потеря сообщений в RabbitMQ (появление dead-letter)
- Резкое падение заказов. Возможные проблемы с API или frontend частью
- Резкий рост заказов. Возможна DDoS атака или спам боты
